# AGENTS.md — Connection Lab

Guidance for AI agents and humans working on this repo. Read this before changing code.

## What this is

An interactive web page that shows what really happens when a laptop fetches `http://example.com/`. The viewer drags a site card onto the laptop; a **protocol-accurate simulation** runs (optionally DHCP first → ARP → DNS over UDP → TCP handshake → HTTP GET → response → FIN teardown) across a small network of isometric devices (laptop on an Ethernet cable or phone on Wi-Fi → home router with NAT → ISP router → DNS resolver / web server, optionally through a VPN server), and the page follows the packets a learner needs in chapters: **Get an address** (DHCP, scenario option `dhcp`: the device starts with no address at all and gets 192.168.1.23, the router and the resolver from the home router), **Find the address** (DNS), **Say hello** (SYN, SYN-ACK, ACK), **Agree on a secret** (TLS 1.3 handshake, HTTPS only), **Get the page** (GET, 200 OK); or, with the scenario option `call`, **Make a call** instead of the page: one second of voice each way as RTP over UDP to a friend's phone, where a lost packet is a gap and nothing is resent; or, with the scenario option `probe`, **Ping** the site (ICMP echo request and reply, the real round trip) or **Trace the path** to it (UDP probes with TTL 1, 2, 3 …; each router whose TTL count hits zero sends ICMP Time Exceeded back, so the TTL that drops at every router finally does something visible). Chapter numbers follow what a run actually has.

Audience: curious learners up to CS-student level. **Simple, fun and educational; playful interactions; never overwhelming.** Learning happens by watching: no narrator, no explanatory pop-ups or captions on stage (the open chapter list is the one place for a sentence, and only for someone who opened it), only short labels on things (device names, "TCP", an address) and what the devices themselves say: one short speech bubble in plain words as a packet sets off, so the basics of a stage can be grasped just by looking, written for someone who has never seen any of this: a run holds still for a moment on what the device sets out to do (`opening`, `OPENING` in timeline.ts) and ends on having got it (`closing`), but only if it did, and it runs on until that has been said (`Timeline.total`, past `settled`, when the last packet is done). An attack holds the same way on what the attackers set out to do (`attackPlans`), and ends on what it did to the run, or that it did nothing (`attackOutcome`), read from what really happened. Every run has a last line, whatever came of it (`closing`), and it ends the run, up for a moment after the last packet (`END_HOLD`). Said long before that, as when a page arrives well before its connection has closed, it has its own moment and is said again at the end. Every situation gets explained, waiting, retrying and failing as much as going well, and correctly: a line that blames the wrong thing counts as unexplained. Speech need not be constant while packets move. A new scenario or option owes a line at the moment that makes it what it is (`speech.ts`; the speech-bubble button in the bar, **Quiet devices**, turns them off). One exception, for a person looking for what a card does: a card held or dragged shows a line on it to its right, clear of the finger, which goes with it even past the edge of the screen (`CARD_HELP` in main.ts). Words on screen stay plain: this document's ISP router and friend's phone are labelled "Internet provider's router" and "Sam's phone", and the Ethernet trailer's chip says "Error check". When in doubt, show less.

## Non-negotiables

1. **Protocol realism.** Every byte shown is a real byte the simulation produced: real header layouts, real field values, real checksums (IPv4, UDP, TCP pseudo-header, Ethernet CRC-32). Never fake a field for the UI. If a teaching need conflicts with realism, expose a *real* knob (e.g. MSS 1460/536) instead of inventing data.
2. **`src/sim` is headless and deterministic.** It must not import from `src/ui` or touch `window`/`document`/`Date`/`Math.random`. ESLint enforces this. All randomness goes through the seeded `Rng` (`src/sim/core/Rng.ts`).
3. **The UI only renders the event log.** The UI never decides protocol behaviour. It reads `SimResult` (events, PDU snapshots, packets) and animates it. "Lose this packet" re-runs the sim with a `FaultPlan`; it does not patch the animation.
4. **Receivers decode bytes.** Devices parse incoming bytes with the same codecs the UI reads; nothing trusts sender-side metadata.
5. **Every field has an explanation.** Each `Field` produced by a describer needs a non-empty `explain` (a test enforces it). Tag fields `importance: 'key'` (the short view) or `'detail'` (full detail).
6. **The scene is a pure function of visual time `v`.** `NetworkScene.render(v)` / `drawPacket(v, peek, pill)` must draw the same picture for the same `v` no matter how you got there. Never accumulate state across frames except the camera smoothing, the peek and pill easing and the site card's drag/spring. This is what makes pause, seeking and a cut mid-run (re-simulate, rebuild the timeline, keep `v`) trivial.
7. **Graphics: simple shapes first** (SVG rects, circles, paths). If a richer illustration would help, write an image-generation prompt for the user (they generate it with ChatGPT) and leave an asset slot. Do not hand-draw complex art.

## UI model (how the animation works)

1. **Story.** `buildStory` picks the packets a learner follows and turns each one's events into steps. A packet with data gets a **card** ("GET /", "example.com?", "200 OK"); an empty segment (SYN, SYN-ACK, ACK) is just its collars, labelled with its flags. A cable cut under a packet (a manual fault) ends its trip with `lost`; whatever the sim sends next (a TCP retransmission after the RTO, the glibc DNS retry after 5 s) is simply the next trip, marked `retry`.
2. **Timeline.** `buildTimeline` lays the trips out one after another in visual seconds. Steps get quicker as they repeat. After a lost trip it inserts a **wait** at the resender: a ring fills (labelled with the real wait), then a surprised "!" and the retry. Knock points (`packetId@link` → progress) only shape the drawing of the fall; the protocol outcome comes from the re-simulation. Adding a knock never changes segments before it (tested).
3. **Scene.** Devices are neutral blocks; the packet is the colourful object. Header pieces are byte-proportional (`TILES_PER_BYTE`); the data card is not to scale. Byte 0 leads. Inside every device the packet lies along the trays (all trays run along x): facing +x on the way out from the laptop, −x on the way back (`trayAngle`). It turns only for a cable that branches off another way (the resolver), swinging round while it drops to the port and back while it rises at the far end (`travelPose`; a test checks the facing never jumps). Layer **trays** (hosts: Ethernet, IP, TCP/UDP, App; routers: Ethernet, IP) show only while a device works on the packet. The old Ethernet sleeve drops and bounces away at every hop; a new one slides on. NAT flips the address on the IP tag (arrow green outward, rust on the way back).
4. **HTTPS (Secure in Setup, scenario option `https`).** Port 443, a real captured TLS 1.3 session (`scripts/capture-tls.mjs`). Each side sends its captured flight once the other side's earlier flights have arrived, and learns what the other said only by decrypting its records with the session's traffic secrets (the key-log approach: the ECDHE exchange that produced them cannot be redone). The story opens every segment's records to name it (`labelTls`): hellos travel open; the certificate, signature, Finished, the GET, the page and the close are **locked** cards, with their own `lock` and `unlock` steps (`lockPose`): a physical padlock drops on open, the session key flies in and turns, the shackle snaps shut and the card goes dark; at the far end the same-shaped key opens it and the padlock lifts away. Each end gets its key when it has read the other side's last open hello (`Timeline.keys`): both compute the same secret, so the keys match. Routers never see inside, not even when you peek. Several packets of one flight are numbered and only the last gets a reaction (`Trip.quiet`).
4. **Interaction.** Dragging a card starts a run, and the "+ action" on an idle device adds a job during it; everything else lives in the bar: ⏮ ⏸ ⏭, then popups for **speed** (0.25×, 0.5×, 1×, 2×), **Tools** and **Setup**, then ♪ and ↺. Every button keeps its place and size from the start, greyed out when it does nothing, so the bar never moves. From 900px wide the "?" stands alone in the bottom right corner, level with the bar (`wideEnough` in main.ts and the same width in app.css), since a narrower bar would reach it; below that it ends the bar, and from 830px down the bar has two rows; "Follow packet" sits apart, top right, after you move the view. New playback controls go in the bar, tools in the Tools popup, things that change the next run in the Setup popup. The page needs a mouse or a touch screen: starting a run is a drag, and a way to do all of it by keyboard alone is deliberately out of scope.
   - **Cards:** the camera sets their size, up to `CARD_MAX_PX` (160px wide) on screen: past that `cardFit` draws them down, and the stack with them around its middle, so a big screen does not get huge cards. A phone's camera is further back and never reaches it.
   - **Site card:** rests between the laptop and the phone. Drop it on the **laptop** (Ethernet cable) or the **phone** (Wi-Fi; scenario option `from`); the device not used greys out. On Wi-Fi the packet flies through the air in a teal **Wi-Fi sleeve** (802.11 header 32 B incl. LLC/SNAP) and the home router swaps it for an orange Ethernet sleeve (`Frame` on wrap/unwrap steps, `frameAt(seg)`). When a run ends the card floats back and the table keeps the final picture (`idleV`), ready to go again.
   - **Second visit:** drag the card in again and the device still remembers the address (scenario option `revisit`), so it skips the lookup and ARP. It goes back to the address it remembers (`knownIp`), which need not be the one this run's lookup would give: a site can have several, and the one server holds them all. It lasts for the DNS record's real TTL (`Story.dnsTtl`), per device and site. Tap a remembered screen between runs to forget.
   - **Setup popup** (between runs only; changing it mid-run would rewrite what happened), a list with a line on what each one does: **Secure page (HTTPS)**, **Bigger page** (the first website, whose reply needs numbered packets: each fills a band of a sheet of paper beside the device (`paper.ts`), a missing one leaves a torn gap, and the finished sheet slides into the screen. Dragging the **photo card** instead of the site card asks for a real JPEG, a cat on this page's own site, 24 packets: from its first packet on the reply is one `flow` step (`gatherStream`, `planFlow`): the camera pulls back and the packets and their ACKs stream along the cables as small blocks, in their real order, each part filling its strip of the real picture), **Satellite internet**, **VPN**, **New on the network** (DHCP, option `dhcp`: chapter "Get an address" first; the OFFER and ACK are cards that appear at the home router; then the story option `StoryOptions.arp`: the ARP exchange that finds the router's MAC is followed too, as chapter "Find the router" before the DNS question; an ARP trip has no IP or transport pieces, `Trip.l4` is `'none'`) and **DNS has to ask around** (option `cold`, below; the three name servers stand behind the resolver, `POS`/`UPSTREAM_KINDS` in timeline.ts, and are off the table otherwise). What is on shows as badges on the card. Trips are told in the order their packets first took to a cable (`Trip.sent`), so a question made before the router's address was known comes after the ARP that found it.
   - **The map reveals itself** (`Timeline.reveals`, `Timeline.laid`, `NetworkScene.present`): every run starts with only your own devices (those with `actions`) and any attackers on the table; before the first packet over a cable sets off, the cable is laid out and the device at the far end springs up, so you see where it is going before it goes. The packet does not wait for this. It is a pure function of `v`, so stepping back takes it away again. Do not put CSS transitions on anything the scene sets every frame: restarted each frame they split the page into layers, and what is on top flickers. What a run showed stays until the next run starts (`setRevealed`), which is also what the tools and the things you drag between runs can reach: before the first run nothing beyond your devices is on the table to cut, spy on, stretch or shake. "Show all" and the whole-map view frame what is on the table right now, not the network it could become (`frameTable`); the follow camera's scale still comes from all of it (`overview`), so it does not pulse as things appear.
   - **The "?" panel** (`LINKS`, `PRIVACY` in main.ts): who made this, where to find them, what the page stores, and the version from package.json. `LINKS` points at the repo; Instagram and a coffee link go there too if wanted. `PRIVACY` must stay true: it says there are no cookies and nothing leaves the browser, so anything that changes that changes it first.
   - **Themes**: `data-theme` on the root element, set from the moon/sun button and remembered; until then it follows the system. Colours are tokens at the top of `app.css`. Whatever lies on the table uses `--ink`; what stays paper in the dark (address cards, sheets, speech bubbles) uses `--card-ink`.
   - **Attackers** (the Attack popup, `attacks` in main.ts; scenario option `attacks`, `Scenario.attackers`, `LinkSpec.overheardBy`): set like the Setup, between runs. Each one puts a real device on the table at a fixed spot, the same shapes as the others in red with red cables and a red terminal, and it stays from run to run until it is switched off or the table is reset. Everything happens in the simulation on pretend devices: this page teaches ideas and is no tool. **Stranger:** a radio with no connection, placed in earshot of the open Wi-Fi: `Link` hands it a copy of every frame and `Device.overhear` checks the FCS and logs it. It sends nothing, so it cannot change a run (`src/ui/attacks.test.ts` compares every frame), the run stays step by step, and what it reads comes from `seenOn` as for the spyglass (`Story.heard`, `listenReadout`), shown in a red terminal under it, pointing up at its name, in one shape with it, which stays there when the camera follows the packet away. It waits rather than stick out from behind the bar. Only the phone is on the Wi-Fi: a laptop run leaves it with nothing. **Scanner:** a SYN by hand to each port (`startPortScan`). A closed port really answers with a reset (`Host.refuse`, RFC 9293) and a connection really ends on one, telling whoever is using it; a port that never answers is listed as `no answer`; the host's own TCP resets any SYN-ACK, so the hello is never finished. **Botnet:** three bots send real junk datagrams (`startFlood`) at the web server, whose line turns thin with a finite buffer while it is under attack: an honest knob, like `THIN_QUEUE`, at a scale where every packet can be drawn, and the ratio of flood to line is what matters. The page's packets really are thrown away and resent, and it comes when the flood is over; a VPN takes another cable to the server and misses it. Scanner and bots are jobs of their own, numbered after the first and before anything dropped in (`Story.attackers`), and since they are already at it when the run starts, the whole run is `traffic`.
   - **Adding a second action** (`deviceActions`, `joinIn`, `joined` in main.ts; `NetworkScene.actionSpots`; scenario option `joins: [{ device, job, at }]`, `Scenario.companions`): during a run every device with nothing to do has a "+ action" button with an arrow to it, on the one side of it that stands clear of everything this run can put on the table (`actionSide`, kept for the run). It moves only as its device does: with the device out of view, or behind the bar, there is no button, and to add an action you look at the device. It gets smaller as the camera goes back, with a 48px tap area. It opens what that device can do (`HomeDevice.actions`), and picking one starts it there at once, once per device and run, with no VPN and nothing remembered. With more than one action going the default view is the whole map, which a viewer can still take over. It works by re-running the simulation with the new job starting just after the last frame on screen (`joinAt`), which must keep what came before byte for byte (`src/sim/join.test.ts`). The story is built for the first job alone and whatever joined goes after it (`buildStory`), so adding one cannot change what was told. `buildTimeline(story, knocks, stretch, drops)` keeps everything up to the first of `drops`, the visual second each device had its action added, lets the step under way finish, and runs all that is left of every job as one `flow` step, chapter `traffic` ("All at once"): small blocks in one colour per device (`HomeDevice.color`; the friend answering a call keeps its own colour), each job only waiting for its own packets, so they go side by side rather than in the real order across jobs. Each way along a cable takes one block at a time: a block waits at the device before it for the first free slot (`freeSlot`), which can only hold it up behind blocks ahead of it, so a cut cannot move what was seen. Small blocks ride on their own side of the cable (`onLane`), so opposite ways pass each other; that goes for every stream, not only the traffic. No layers, address swaps or tapping packets open in there: that is the trade for watching it all at once, and a run nobody drops into is untouched (`src/ui/join.test.ts`). Each device's page shows when its last packet lands (`Timeline.pages`, `Story.fetched`) and its DNS answer when that lands (`Timeline.answers`), a dropped-in ping or trace prints on its own terminal (`Story.joinProbes`, `Timeline.joinReadouts`), and a call keeps its notes. Packets are numbered per job and sender, so a packet that is never sent renumbers nobody else's, and `decided` holds through a cut during the traffic. The sheet, numbered parts and TLS labels are the first device's only, but each device has its own screen (`Story.screens`), and the friend's phone comes onto the table when a call is dropped in. The one web server holds every address its sites can resolve to (`IfaceSpec.aliases`) and serves each by the `Host` header (`http-server.responses`), as one server hosting several sites does; a socket answers from the address it was asked on. A second call finds the friend busy: it talks, hears nothing and hangs up.

The arrow beside it in the Setup (`smartMenu`, `Menu.row`) chooses the broker (home, or scenario option `cloud`: out on the internet, `outsider`, `broker.example`, always in the resolver's cache) and the QoS (scenario option `qos`), remembered in `net.smart`. The sensor publishes to a topic, and the broker sends each subscribed app its own copy: laptop and phone both run an app, each on a job of its own, and neither hears from the sensor directly. A cut made during a run, even before anything has left, comes after that (`Timeline.startsAt`, `seenSoFar`), or nobody would ever have connected. **QoS:** each connection is a leg with its own exchange: nothing at 0, PUBACK at 1, PUBREC, PUBREL, PUBCOMP at 2, where the broker passes a message on only once it is released. The exchange on the sensor's connection is told in full and the same steps with each app run as small named blocks (`appLeg`, `namedAcks`), or QoS 2 would take minutes. TCP's own ACK goes by first, then the program's answer. **An app that is away:** QoS only shows when a connection is gone, because while one is up TCP resends what is lost at any QoS, so a line cut during a run only delays a reading. A line already cut when a reading is taken has been out since `OFFLINE_AT`: keep-alive (PINGREQ, then no PINGRESP) tells the app, and the broker gives up one and a half keep-alives after it last heard from it. A connection TCP gives up on or that is reset goes the same way, on both sides. At QoS 0 the broker drops what comes for it (`mqtt-missed`). At QoS 1 and 2 it keeps it (`mqtt-held`), because an app has no clean session. Meanwhile the app keeps trying to connect, so SYNs fall off the cable with their rings; mend the cable during a run and it says hello, CONNECT and CONNACK with its session kept, needs no SUBSCRIBE, and gets what was held. A reading is one story, so everything on any connection is told in order (`trip`, for `quietUntil`). The readings are `page` chapter trips named "Send the reading", each with a card such as "21.5 °C" (`Message` kind `reading`), and each app's screen shows the value (`Screenful.pageTitle`, from `mqtt-received`). The reading itself comes from the seeded Rng, so a re-simulation after a cut keeps it. VPN, HTTPS, DHCP and a cold resolver are for a browser and are ignored; slow lines, a noisy Wi-Fi, the tools and the attackers all apply. A second action cannot be added during a reading, and a reading cannot be taken during a run. With it set the phone's Wi-Fi is the real 802.11 link layer: every unicast data frame that gets across is answered by a real 14-byte Ack control frame (packet kind `wifi-ack`, label "Wi-Fi ACK") SIFS after its last bit, and each frame on the air, data or Ack, is lost with that chance (`drop` reason `interference`, at the receiver, decided by hash per packet and attempt, `faults.ts#lostToNoise`). A sender that hears no Ack within the Ack timeout (50 µs) sends the same frame again with the Retry bit set, after a backoff of 9 µs slots drawn (by hash too) from a contention window that doubles 15 → 1023, up to 7 times (sim events `wifi:retry` with `attempt` and `backoff`, `wifi:ack` when the Ack comes), then gives up (`drop` reason `retry-limit`, at the sender) without TCP or DNS hearing of it: they notice later, by their own timers. An Ack lost on the way makes the sender resend a frame that had arrived; the receiver spots the copy by (transmitter, sequence number) and drops it (`drop` reason `duplicate-frame`), acknowledging it all the same. With noise 0 (the default) no Ack is sent and nothing is retried: today's simplification kept, so the normal runs stay byte for byte as they were. The story carries it (`Story.noise`): a frame lost on the air is a `lost` step that does not end the trip, the radio's retry is the next `travel` on the same link with `retry: true`, a copy that was only resent because its Ack was lost is left out, and only `retry-limit` ends the trip as lost. Ack frames are not followed as trips. `Trip.retry`/`timedOut` stay false for link retries: those are TCP's and DNS's.

The layout moves with the pointer; the simulation catches up when the router is let go.

## Key concepts

- **Packet vs. PDU snapshot.** A `PacketInfo` is a logical packet (`pk12`, label "SYN"). It keeps its id across hops. A `PduSnapshot` (`pdu40`) is the exact bytes at one moment (e.g. the frame on one link). Every `encapsulate`/`decapsulate`/`tx`/`forward`/`nat:translate` event points at a snapshot. Retransmissions are new packets with `retransmitOf`.
- **Layer numbers** in the sim are TCP/IP 5-layer (1 physical … 5 application).
- **Stream packets** (`kind: 'stream'`) are application bytes handed to TCP or reassembled from it; they never cross a link.
- **Determinism / faults.** Same scenario + seed + FaultPlan ⇒ identical event log. Random loss is keyed by `hash(seed, link, packet)` so adding a manual fault never changes events before it (tested).

## How to add things

- **A new protocol:** add `src/sim/proto/<p>.ts` with `build`, `parse`, `describe` (absolute offsets, explanations), wire it into `decode.ts`, add the name to `Protocol` and `PROTOCOL_LAYER`, add codec tests with known-good bytes.
- **A new scenario:** add `src/sim/scenarios/<name>.ts` returning a `Scenario` (devices with ifaces/routes/ARP seeds/apps, links with real-ish speeds and delays). Add app behaviour in `stack/apps.ts` if needed and a test in the style of `src/sim/run.test.ts`. In the UI, give new device kinds a position in `timeline.ts#POS` (along the grid's axes where the table allows; attackers' and a few backbone cables run at an angle), a height in `DEVICE_TOP` and a shape in `NetworkScene#buildDevice` in the bold-outline style (`slab`, `panel`, `groundShadow` in `prims.ts`, details with `plate` and `stud`, colours as the `.dev-*` rules in app.css: dark outline, warm body, one blue); teach `story.ts#chosen` which packets to follow.
- **A new device of your own:** add an entry to `HOME_DEVICES` in `scenarios/fetchWebPage.ts` (how it connects, its port on the home router, its link, its `actions`); everything from the router's routes and DHCP to the "+ action" button, the drop target and its colour follows from that. Give it a place in `timeline.ts#POS` by its id, and a new kind a height in `DEVICE_TOP` and a shape in `NetworkScene#buildDevice`. `src/ui/devices.test.ts` runs a third device this way, in the tests only. A second radio is not yet one shared air: each link's noisy Wi-Fi is its own, and the "open Wi-Fi" note and the stranger's beam are drawn for `wlan`.
- **A new kind of step:** add it to `Step` in `story.ts` (from the events), give it a duration in `timeline.ts#DUR` and a position, and draw it in `NetworkScene` (`parts`, `drawPacket`). Keep it a pure function of `v`.

## Real-world facts and simplifications (keep honest)

- example.com resolves to Cloudflare addresses; captured values live in `src/sim/scenarios/exampleComCapture.ts` (re-capture with the script). The HTTP response is the verbatim captured bytes (chunked, 932 bytes as of 2026-10-29).
- Home public IP `203.0.113.7` and ISP backbone `198.51.100.0/24` are RFC 5737 documentation ranges standing in for real ones. The friend's phone has `198.51.100.42` from the same block and the name `sam.example`, in the `.example` top-level domain RFC 2606 reserves for documentation; its A record (TTL 300) is invented and always in the resolver's cache, since no real walk exists for it. MAC addresses are plausible but invented.
- The laptop behaves like Linux: TTL 64, ephemeral ports 32768–60999, SYN options MSS/SACK-permitted/timestamps/NOP/window scale 7, glibc DNS timeout 5 s × 2 attempts. TCP RTO follows RFC 6298 (1 s minimum). After a timeout everything still out goes again as the window allows, and a timestamp echo lets the timer recover once a resend is answered, so a short outage costs about its own length plus a timer. The VPN server is a hop both ways, and the web server advertises its normal MSS, knowing nothing of the tunnel.
- Under random loss the DNS lookup often fails: like glibc, the stub resolver sends the question at most twice, 5 s apart. That is the real behaviour, not a bug.
- HTTPS replays a captured session, so its random values, certificate and keys are the real ones from the capture day; the handshake secrets are taken from the key log rather than re-derived from the ECDHE exchange. Cipher suite TLS_AES_128_GCM_SHA256. The card says "hello" for ClientHello/ServerHello, "certificate", "signature" (CertificateVerify), "done" (Finished), "ticket" (NewSessionTicket), "bye" (close_notify).
- The VPN is real WireGuard transport messages (ChaCha20-Poly1305, padded to 16 bytes), but the tunnel is already up: the Noise handshake is not shown and the session keys come from the seeded Rng. MSS is 1380 in a tunnel, as for WireGuard's usual MTU of 1420. Sim tests open the sealed bytes from the ISP line with the session key.
- The phone's Wi-Fi is an open network: real home Wi-Fi encrypts frame bodies (WPA2/WPA3 adds a CCMP header and an 8-byte MIC). No QoS field. The link-layer Ack frames are real (IEEE 802.11-2020 §9.3.1.4: Frame Control d4 00, Duration 0, the receiver's address, FCS) but left out unless `noise` is on, so a quiet Wi-Fi stays today's perfect cable through the air. A real home router bridges its Wi-Fi and Ethernet ports into one network with one address; the sim models that bridge as two interfaces sharing 192.168.1.1 plus a host route to the phone. The phone sends the same captured request bytes as the laptop.
- Simplifications to state in the UI: the real internet path has ~10 routers, we show one ISP router; the resolver answers from cache unless `cold` is on; the LAN is wired Ethernet (Wi-Fi uses 802.11 framing); no IPv6, no TLS in this scenario; ACKs are sent immediately (Linux "quickack" at connection start), not delayed.
- The cold resolver's three upstream servers are the real ones a walk reached on the capture day (`dnsTraceCapture.ts`: a.root-servers.net, then the TLD server and the site's name server its referrals named first with glue), with their real referral and answer bytes and measured round-trip times; the resolver picks the next server from the glue in the bytes, as the capture did. A real resolver talks to many more servers over time, uses QNAME minimisation, EDNS (bigger replies, DNSSEC) and TCP when a reply is truncated; the three hops are the classic textbook walk. The root's `.com` referral is truncated (TC=1, 489 bytes: 13 servers' glue does not fit in 512 bytes without EDNS); the resolver uses what fit, where a real one would ask again over TCP. Replies with a CNAME (info.cern.ch) are followed, but the resolver's own answer to the laptop carries only the addresses. The resolver sends its questions from one port and its service address 1.1.1.1; real resolvers randomise the port per question. When the walk's answer puts another of the site's addresses first, the web server holds that address as well.
- A quiet Wi-Fi link (noise 0) is modelled full duplex with an Ethernet-style preamble; real 802.11 is half duplex with CSMA/CA, and every data frame is answered by a link-layer ACK frame.
- A noisy Wi-Fi (option `noise`) uses the 2.4 GHz timings: SIFS 10 µs, slot 9 µs, DIFS 28 µs, an Ack timeout of 50 µs (SIFS + slot + the PHY's delay), contention window 15 doubling to 1023, dot11ShortRetryLimit 7 retries after the first try. Both directions share one air (half duplex): a data frame waits DIFS after the air falls silent and an Ack only SIFS, so the Ack always gets in first; frames take their turn in the order they are handed in and never collide (no carrier sense beyond that, no RTS/CTS). A frame to everyone (the access point's ARP request) is sent once and never acknowledged, as in 802.11. The radio keeps one rate (no rate adaptation), the bodies stay open (no CCMP), and the Duration field still says 44 µs, the 5 GHz figure from before, so a quiet run's bytes stay the same. A copy sent again is a new frame on the air (Retry bit, fresh FCS) but keeps its 802.11 sequence number; a real receiver keeps a small cache of recent (transmitter, sequence) pairs, here only the newest per transmitter.
- No RACK/TLP: a loss at the tail of a flight waits for the 1 s RTO, where modern Linux sends a probe after about two round trips.
- The thin pipe (option `thin`) is a 20 Mbit/s line whose ISP-side port buffers 8 frames (`THIN_QUEUE`) and tail-drops the ninth: with Linux's initial window of 10 the tenth packet of the first burst falls off, then the FIN at the tail of the second, and TCP mends both with a fast retransmit and NewReno recovery. 8 is a deliberately small, honest knob: a 25-packet photo never stacks more than 8 frames at the port, so a bigger buffer would never overflow here. Real home routers and DSLAMs often buffer hundreds of frames, which hides the loss and makes the queueing delay grow to hundreds of milliseconds instead (bufferbloat). No AQM (CoDel, PIE), no ECN, no per-flow fairness: plain FIFO tail drop, the one frame being clocked out not counted in the buffer.
- The FIN always travels in its own segment; Linux piggybacks it on the last data segment when it can.
- Routers really send ICMP Time Exceeded when a TTL runs out (from the address the packet arrived on, RFC 1812), hosts and routers answer echo requests, and hosts send Port Unreachable for a UDP datagram nobody listens to. A closed TCP port answers with a reset (`Host.refuse`), and a connection only takes a reset at exactly the sequence number it expects (the strict rule of RFC 5961; the challenge ACK for one that is merely in the window is left out). But: no ICMP for an unreachable address, no rate limiting except on a server under attack (`icmpLimit`: one error a second to any one address, Linux's default for this message), and an error quotes the offending datagram's IP header plus 8 bytes (RFC 792, the classic), where Linux quotes up to 576 bytes as RFC 1812 allows. No ICMP error is ever sent about an ICMP error or a broadcast (RFC 1122).
- Ping is like Linux `ping -c 4`: 56 data bytes (a 16-byte struct timeval of the sending time, two little-endian 8-byte integers as on x86-64, then the bytes 0x10 … 0x37), so 64 bytes of ICMP and 84 of IP; the identifier is a process id (from the seeded Rng), sequence numbers count from 1, requests go one second apart with Don't Fragment set, and the round trip is measured from the timestamp the reply echoes. The clock in the timestamp is the simulation's (seconds since the run started), not the wall clock. After the last request ping waits a second for its reply, then sums up (sent, received, loss, min/avg/max).
- Traceroute is like Linux `traceroute`: UDP probes from one ephemeral port to port 33434 and up, one port per probe (the quoted destination port is how an answer is matched to its probe), 60-byte IP packets whose 32 data bytes are 0x40, 0x41, … ("@ABC…"), three probes per hop, TTL 1, 2, 3 … up to `maxHops`; it stops after the hop whose answer is the destination's Port Unreachable. Simplifications: one probe in flight at a time, the next sent when the previous is answered or after 1 s (Linux keeps up to 16 in flight and waits up to 5 s), and no ICMP-echo or TCP-SYN probe modes.
- The home router and the VPN server NAT ICMP the way netfilter does: an echo's identifier is translated like a source port (and, as for ports, always to a new one here), and an ICMP error coming back is matched to its inside host by the header it quotes (the quoted source port, or echo id, and destination), that quote being translated back too, with the quoted IP checksum recomputed, the quoted UDP checksum updated incrementally (RFC 1624: the data it covers is not there) and the ICMP checksum recomputed over the whole message. An ICMP error from a host inside is dropped at the NAT rather than translated: it would leave with a private address.
- The NAT always picks a new outside port, a deliberate, visible knob; Linux MASQUERADE keeps the original port unless it collides, though some consumer NATs change it too.
- A name the resolver does not know gets a real NXDOMAIN answer (rcode 3), and the browser gives up on it like a real one; the stub resolver treats an answer without addresses as a failure. A cold resolver whose upstream server stays quiet asks it once more after 2 s, then answers SERVFAIL (rcode 2).
- The voice call (option `call`) is real RTP (RFC 3550) with real G.711 µ-law audio at 64 kbit/s, the landline telephone codec: 8000 one-byte samples a second, 160 per 20 ms packet (RFC 3551's default packetisation and static payload type 0), sequence number, timestamp (+160 per packet) and SSRC starting at random values from the seeded Rng as the RFC asks, the marker set on the first packet. The two clips are synthesised, not recorded (a spoken-rhythm melody of buzzy tones, `scripts/make-voice-clip.mjs`, encoded with the standard µ-law formula). What is left out: a real app would use Opus, encrypt with SRTP, send RTCP reports, hold a jitter buffer and find the peer by SIP or WebRTC signalling; here DNS finds the friend's name, packets are played as they come, a skipped sequence number is a gap nobody fills, and each side hangs up on its own once both clips are through (its own sent and the other's length heard from its first packet; a caller who hears nothing gives up two seconds after its clip). Both sides use the one well-known port 5004 on the friend's side; nothing is encrypted, so the spyglass hears the voice. With a VPN the opened call leaves the VPN server by its default route through the ISP router (it has no cable of its own to the friend).
- MQTT (option `reading`) is real MQTT 3.1.1 on port 1883 with real bytes, but only what a reading needs: no retained messages, no last will, no wildcards in a topic filter, no user name or password. The variant without TCP, MQTT-SN, is another protocol and is not here. A real broker on the internet would use TLS on 8883 and a login; here it is plain so that the spyglass and the stranger can read it, which is exactly what happens without those. The keep-alive is 3 s where 60 s is usual, so an outage is noticed within a short story, and it only runs until the reading, so a run needs no PINGREQ of its own: a line cut during a run is left to TCP. An app comes back once, on one connect with TCP's own SYN resends, then gives up, where a real one would go on trying for ever: a run has to end. A message sent on a connection that dies before it is answered is not sent again with the DUP flag, because a reading never goes out on a connection about to die, so "QoS 1 can arrive twice" is said but never shown. Connections are simply up when a run starts, as in any home, where they were opened long ago. A broker at home is reached by its address, as is usual for one with a fixed address; its name would come from mDNS. The cloud broker's name is invented in the `.example` domain and its address is from the RFC 5737 documentation block. The value is a made-up room temperature, 18.0 to 23.9 °C, as plain text; the topic is `home/livingroom/temperature`. The router's switch knows which port each device is on, where a real one learns it from the frames it sees, and it passes on only ARP broadcasts that are not for the router, not all of them. The sensor's link is its own, 72 Mbit/s at 2.4 GHz: a real sensor shares one air with the phone, and the home router bridges them, as for the phone.
- DHCP (option `dhcp`) is the real four-message exchange with real bytes: DISCOVER and REQUEST broadcast from 0.0.0.0:68 to 255.255.255.255:67, OFFER and ACK unicast to the client's MAC with the offered address as IP destination (what ISC dhcpd and dnsmasq do when the broadcast flag is clear); the client asks for options 1, 3, 6, 15, 28, 51, 54 like dhcpcd/dhclient and resends after 4, 8, 16 s with no ±1 s jitter. The server has fixed leases by MAC (192.168.1.23 for the laptop, .42 for the phone), lease 1 day; no pool, no DECLINE/ARP probe of the new address, no renewal (T1/T2) or RELEASE is shown. A real client's DNS resolver and default route then come from the lease, as here.
