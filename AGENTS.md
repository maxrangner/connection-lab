# AGENTS.md — How the Internet Works (interactive educator)

Guidance for AI agents and humans working on this repo. Read this before changing code.

## What this is

An interactive web page that shows what really happens when a laptop fetches `http://example.com/`. The viewer drags a site card onto the laptop; a **protocol-accurate simulation** runs (optionally DHCP first → ARP → DNS over UDP → TCP handshake → HTTP GET → response → FIN teardown) across a small network of isometric devices (laptop on an Ethernet cable or phone on Wi-Fi → home router with NAT → ISP router → DNS resolver / web server, optionally through a VPN server), and the page follows the packets a learner needs in chapters: **Get an address** (DHCP, scenario option `dhcp`: the device starts with no address at all and gets 192.168.1.23, the router and the resolver from the home router), **Find the address** (DNS), **Say hello** (SYN, SYN-ACK, ACK), **Agree on a secret** (TLS 1.3 handshake, HTTPS only), **Get the page** (GET, 200 OK). Chapter numbers follow what a run actually has.

Audience: curious learners up to CS-student level. **Simple, fun and educational; playful interactions; never overwhelming.** Learning happens by watching: no narration, no explanatory pop-ups or captions, only short labels on things (device names, "TCP", an address). When in doubt, show less.

## Non-negotiables

1. **Protocol realism.** Every byte shown is a real byte the simulation produced: real header layouts, real field values, real checksums (IPv4, UDP, TCP pseudo-header, Ethernet CRC-32). Never fake a field for the UI. If a teaching need conflicts with realism, expose a *real* knob (e.g. MSS 1460/536) instead of inventing data.
2. **`src/sim` is headless and deterministic.** It must not import from `src/ui` or touch `window`/`document`/`Date`/`Math.random`. ESLint enforces this. All randomness goes through the seeded `Rng` (`src/sim/core/Rng.ts`).
3. **The UI only renders the event log.** The UI never decides protocol behaviour. It reads `SimResult` (events, PDU snapshots, packets) and animates it. "Lose this packet" re-runs the sim with a `FaultPlan`; it does not patch the animation.
4. **Receivers decode bytes.** Devices parse incoming bytes with the same codecs the UI reads; nothing trusts sender-side metadata.
5. **Every field has an explanation.** Each `Field` produced by a describer needs a non-empty `explain` (a test enforces it). Tag fields `importance: 'key'` (the short view) or `'detail'` (full detail).
6. **The scene is a pure function of visual time `v`.** `NetworkScene.render(v)` / `drawPacket(v, peek, pill)` must draw the same picture for the same `v` no matter how you got there. Never accumulate state across frames except the camera smoothing, the peek and pill easing and the site card's drag/spring. This is what makes pause, seeking and a cut mid-run (re-simulate, rebuild the timeline, keep `v`) trivial.
7. **Graphics: simple shapes first** (SVG rects, circles, paths). If a richer illustration would help, write an image-generation prompt for the user (they generate it with ChatGPT) and leave an asset slot. Do not hand-draw complex art.

## UI model (how the animation works)

1. **Story.** `buildStory` picks the packets a learner follows and turns each one's events into steps. A packet with data gets a **card** ("GET /", "example.com?", "200 OK"); an empty segment (SYN, SYN-ACK, ACK) is just its collars, labelled with its flags. A cable cut under a packet (a manual fault) ends its trip with `lost`; whatever the sim sends next (a TCP retransmission after the RTO, the glibc DNS retry after 5 s) is simply the next trip, marked `retry`.
2. **Timeline.** `buildTimeline` lays the trips out one after another in visual seconds. Steps get quicker as they repeat. After a lost trip it inserts a **wait** at the resender: a ring fills (labelled with the real wait), then a surprised "!" and the retry. Knock points (`packetId@link` → progress) only shape the drawing of the fall; the protocol outcome comes from the re-simulation. Adding a knock never changes segments before it (tested).
3. **Scene.** Devices are neutral blocks; the packet is the colourful object. Header pieces are byte-proportional (`TILES_PER_BYTE`); the data card is not to scale. Byte 0 leads. Inside every device the packet lies along the trays (all trays run along x): facing +x on the way out from the laptop, −x on the way back (`trayAngle`). It turns only for a cable that branches off another way (the resolver), swinging round while it drops to the port and back while it rises at the far end (`travelPose`; a test checks the facing never jumps). Layer **trays** (hosts: Ethernet, IP, TCP/UDP, App; routers: Ethernet, IP) show only while a device works on the packet. The old Ethernet sleeve drops and bounces away at every hop; a new one slides on. NAT flips the address on the IP tag (arrow green outward, rust on the way back).
4. **HTTPS (Secure in Setup, scenario option `https`).** Port 443, a real captured TLS 1.3 session (`scripts/capture-tls.mjs`). Each side sends its captured flight once the other side's earlier flights have arrived, and learns what the other said only by decrypting its records with the session's traffic secrets (the key-log approach: the ECDHE exchange that produced them cannot be redone). The story opens every segment's records to name it (`labelTls`): hellos travel open; the certificate, signature, Finished, the GET, the page and the close are **locked** cards, with their own `lock` and `unlock` steps (`lockPose`): a physical padlock drops on open, the session key flies in and turns, the shackle snaps shut and the card goes dark; at the far end the same-shaped key opens it and the padlock lifts away. Each end gets its key when it has read the other side's last open hello (`Timeline.keys`): both compute the same secret, so the keys match. Routers never see inside, not even when you peek. Several packets of one flight are numbered and only the last gets a reaction (`Trip.quiet`).
4. **Interaction.** Dragging the card starts a run; everything else lives in the bar: ⏮ ⏸ ⏭, then popups for **speed** (0.5×, 1×, 2×), **Tools** and **Setup**, then ♪ and ↺. Every button keeps its place and size from the start, greyed out when it does nothing, so the bar never moves; "Follow packet" sits apart, top right, after you move the view. New playback controls go in the bar, tools in the Tools popup, things that change the next run in the Setup popup.
   - **Site card:** rests between the laptop and the phone. Drop it on the **laptop** (Ethernet cable) or the **phone** (Wi-Fi; scenario option `from`); the device not used greys out. On Wi-Fi the packet flies through the air in a teal **Wi-Fi sleeve** (802.11 header 32 B incl. LLC/SNAP) and the home router swaps it for an orange Ethernet sleeve (`Frame` on wrap/unwrap steps, `frameAt(seg)`). When a run ends the card floats back and the table keeps the final picture (`idleV`), ready to go again.
   - **Second visit:** drag the card in again and the device still remembers the address (scenario option `revisit`), so it skips the lookup and ARP. It lasts for the DNS record's real TTL (`Story.dnsTtl`), per device and site. Tap a remembered screen between runs to forget.
   - **Setup popup** (between runs only; changing it mid-run would rewrite what happened): **Secure** (HTTPS), **Bigger page** (the first website, whose reply needs numbered packets: each fills a band of a sheet of paper beside the device (`paper.ts`), a missing one leaves a torn gap, and the finished sheet slides into the screen. Dragging the **photo card** instead of the site card asks for a real JPEG, about 25 packets: from its first packet on the reply is one `flow` step (`gatherStream`, `planFlow`): the camera pulls back and the packets and their ACKs stream along the cables as small blocks, in their real order, each part filling its strip of the real picture), **Satellite**, **VPN**, **Together** (below), **No address** (DHCP, option `dhcp`: chapter "Get an address" first; the OFFER and ACK are cards that appear at the home router), **Cold resolver** (option `cold`, below; the three name servers stand behind the resolver, `POS`/`UPSTREAM_KINDS` in timeline.ts, and are off the table otherwise) and **Show ARP** (a story option, `StoryOptions.arp`: the ARP exchange that finds the router's MAC is followed too, as chapter "Find the router" before the DNS question; an ARP trip has no IP or transport pieces, `Trip.l4` is `'none'`). What is on shows as badges on the card. Trips are told in the order their packets first took to a cable (`Trip.sent`), so a question made before the router's address was known comes after the ARP that found it. **Together** (scenario option `together`, `Scenario.companion`): the other device opens plain http://example.com/ 4 ms after the first (`COMPANION_DELAY`), with no VPN and nothing remembered, so the two fetches interleave and the home router has two conversations to tell apart: two inside addresses, two outside ports, one public address. `Story.clients` lists both; every trip knows whose fetch it is (`Trip.client`, a reply by the outside port the router gave the request, `assignClients`), the hello-ending ACK is flagged (`Trip.hello`), and the sheet, the stream, numbered parts and TLS labels are the first device's only. When the first device's site is another server's, that server holds example.com's address as an alias (`IfaceSpec.aliases`) and serves it by the `Host` header (`http-server.responses`), as one server hosting several sites does; a socket answers from the address it was asked on.
   - **Tools popup:** spy and scissors. Pick one (it stays lit and the popup stays open, the cursor changes, the line under the pointer lights up), then click as many lines as you like; clicking a line again undoes it. Closing Tools with its own button, or Esc, puts the tool down (opening another popup only hides Tools); what you did stays. Tools work any time: mid-run, `seenSoFar(tl, v, line)` freezes every frame that has set off (`FaultPlan.decided`) and the change applies from that sim time on (`FaultPlan.cuts`, one entry per line), or from the first frame still to come on that line: a stream spreads microseconds out into seconds, so what has not visibly left yet can be earlier in sim time than what has. `crossings(tl)` lists every frame on a cable, alone or in a stream; whatever looks at the cables goes through it. A test sweeps cuts across every line, moment and setup and checks that nothing already seen changes.
   - **Spy:** one glass, on one line, with its lens on the middle of it. A popup above the bar (`SpyCard`, `spyLog`) shows what anyone on that line can read from each passing frame. It follows the newest read, stays up until dismissed (which also takes the glass off the line), and its arrows step back through the older reads of this run, from the moment the glass went on the line (a glass already there when a run starts reads all of it). What it reads is computed from the real bytes with no keys (`Seen`, `seenOn`): addresses and plain HTTP or DNS; with HTTPS only scrambled bytes, except the site name from the ClientHello's SNI extension (`clientHelloSni`); with a VPN only scrambled bytes to the VPN server. Changes nothing about the run.
   - **Scissors** (cables only; radio cannot be cut): every frame sent on that cable is lost (drop reason `cut`), and whatever is riding it right now falls in where it is (`ridingOn`), also every packet of a stream. Resends back off for real (1, 2, 4 ... s, 60 s at most), each with a longer ring and each trip faster than the last, until the sender gives up or you mend the cable. A cable already cut at the start warms the ARP caches (`warmArp`) so the first thing to fall is a packet you can see.
   - **VPN:** Scenario option `vpn`: every packet of the device goes into a WireGuard tunnel to the VPN server, DNS too. The story has `wrap`/`unwrap` steps with layer `vpn` (they carry the addresses showing from there on, for `addressBefore`). A translucent tube runs along the way from the device to the VPN server (`buildTunnel`). The finished packet gets shut inside a box with a shield on it (`boxFront`/`boxBack` in `drawPose`: the box comes down over the IP, transport and card pieces, which are then not drawn), and its address tag flips to a new one; with a VPN the tag names who each address belongs to (`Story.names`). Past the VPN server the packet is ordinary again, sent from its address.
   - **Satellite:** scenario option `slow`, a geostationary link, 280 ms each way, 25 Mbit/s, drawn as a hop the packet climbs (`Timeline.sky`).
   - **Thin pipe:** scenario option `thin`: the line to the ISP is a 20 Mbit/s DSL line (same 2 ms, `wanDelay` still applies; `slow` wins over it) and the ISP's port onto it has a transmit buffer of `THIN_QUEUE` frames (`LinkSpec.queue`, per direction). The server's burst arrives over the 10 Gbit/s backbone far faster than the line drains it, so frames wait at the port (sim event `queue`: `depth` frames ahead of it, `wait` seconds until its `tx` starts) and when the buffer is full the newcomer is dropped at once (`drop` with reason `queue-full`, at the device, no `tx`): the first natural loss in the app, with no scissors; TCP mends it with dup ACKs and a fast retransmit. The story carries it: `Story.thin`, `Story.links[].queue`, `queued` on a `travel` step (seconds it waited in the buffer, absent when it did not), and a packet the full buffer turned away ends with a `lost` step on the line it was bound for, `at` the drop time, with nothing `seen` (it never reached the cable) and `Trip.droppedAtQueue`, so it can be drawn falling off the tray rather than off the cable. Links without `queue` behave exactly as before (nothing is queued visibly, nothing dropped for want of room).
   - **Cold resolver:** scenario option `cold`: the resolver has nothing cached for the site and really walks the hierarchy with the captured bytes: an RD=0 question to the root server, its referral ("ask .com", the NS records plus glue), the same question to the .com server, its referral to the site's own servers, the question to one of those, the answer; the resolver caches it and only then answers the laptop. Three devices (`root`, `tld`, `auth`, kinds `root-server`/`tld-server`/`auth-server`) stand behind the resolver on their own cables (`up1`–`up3`, one-way delay half the measured round trip); they are in every run and greyed out when cold is off. A referral travels as a card saying who to ask next (`dnsCardLabel`) and gets a `lookup` step at the referring server. `Story.dnsAnswer` is still the laptop's answer (the resolver's walk uses its own app actions: `dns-iterate`, `dns-referral`, `dns-learn`).
   - **Packets:** tap one to pop it open with real sizes, on a cable as well as at a station; the run holds until you close it. Tap a pill and it grows upwards with that piece's key fields, one at a time (`Details`, `detailsAt`): the real fields of the packet as the latest step left it (`Step.details`, from the event's own snapshot), so addresses change at NAT, the TTL drops at each router and a new sleeve has its new MACs. What is sealed in a VPN box says "sealed". The last row of an open pill, "the bytes", opens the **hex view** (`hexCard.ts`, top right): the exact bytes of the packet as the latest step left them (`Step.pdu`, `pduAt`), coloured by piece, the opened piece bright; touching a byte names its field.
   - **Step buttons / arrow keys:** one action at a time (`stepTarget`), and in a stream one packet at a time. Back goes to the start of this action, or within a second of that start to the one before, so a packet never loops. The animation really plays, in 0.22–0.5 s and without sounds, then carries on as it was, playing or paused.
   - **Stretch the cable:** between runs the ISP router can be dragged further away (`data-grab`, `stretchPress` in main.ts; `buildTimeline(story, knocks, stretch)` moves the ISP router and everything beyond it along +x and `NetworkScene.buildDevices` rebuilds the devices when the layout moves). Each tile stands for 50 km of fibre and light in glass does 200 000 km/s (`wanDelayFor`), so the cable's note says its length and one-way delay ("400 km · 2 ms" by default, up to 8000 km · 42 ms); the scenario gets `wanDelay` and the real timers, rings and round trips follow. The layout moves with the pointer; the simulation catches up when the router is let go.
   - **Reset (↺):** back to a clean table from anywhere: settings off, tools and lines cleared, memories gone, the cable its usual length.
   - **View:** drag, pinch or wheel lets go of the follow camera.
5. **An address changing** is the big moment of its step (`swapMoment`, `addressTag`, sound `swap`): the tag swells, the changed field flips over, a fresh teal label lands with a few sparkles, the old label slips out from under the tag, and the tag settles. Routine work, so nothing here may look like an accident: stars and speed lines are for packets that get hit. NAT and the VPN box get extra time the first few times.
   - **ACKs:** the ACK that ends the hello is a whole packet. Every other ACK runs as a small purple block on its own (`smallAcks`, a `flow` step of one packet), so a sender that hears nothing has a visible reason to wait. It carries the label "ACK: got it", as do the first few in a stream, because a coloured block says nothing by itself.
   - **Real time:** the animation stretches time, so a pill under the chapter shows the real clock (`realAt`, a pure function of visual time, from when frames really left and arrived). A satellite says "280 ms" on its arc. The Wi-Fi says "open Wi-Fi": its frames are not sealed here, which is why the spyglass reads them; a home network with a password would seal them.
   - **NAT ports:** the tag shows the port next to the changed address, only during the swap: the port is how the way back is found.
   - **HTTPS:** each end keeps a bow and each hello carries a blade in the sender's colour (`Trip.keyShare`, `halves`), there for any snoop to see; blade and bow make the key. When the laptop reads the end of the server's proof, a stamp shows the name its certificate really covers (`Trip.identity`, `certifiedName`) in place of the 👍.
5. **Servers do their job** (`lookup` steps, `stations.ts`). The packet's card sinks into the server, and the reply trip starts with the work: the resolver's book opens, pages turn, the question runs down the names, the line lights up and the address lifts off (for every answer it sends); the web server tries its slots, a drawer slides out and the page rises from it (once, for the first packet of the reply). Only what the real messages carry is readable; every other line is a grey bar.
5. **Greying out and chapters.** Once a run starts, devices (and their cables) that no trip of this run visits are greyed out, e.g. the DNS resolver on a revisit. The chapter label is a button: it opens a list of this run's chapters to jump to.
5. **Words.** No narrator and no explanatory text on stage. Allowed: device names, names in menus, layer names on trays and pieces, the from/to tag, byte sizes and field names and values when peeking, what a server looks up, timer seconds, the three chapter names.
6. **Emoji statuses** (`timeline.ts#arrivalFace`, `Reaction`), all derived from what really happened: 👍 a reply (or the final handshake ACK) arrives; 😍 the page is complete; 😕 a duplicate, or a page part arriving while an earlier one is missing; 😢 on a packet as it falls off a cable; at the resender's timer, "!" the first time, 😠 when its resend was lost too, 😭 when it gives up. Requests get no reaction. The camera lingers on a reaction between trips. A stream has too many packets for a 😢 or 👍 each: it keeps 😕 and 😍, and the timer's ring (`FlowWait`, when `Trip.timedOut`, after everything on the cables has come off them) with its "!", 😠 and 😭. A ring runs just before the resend it belongs to (`Trip.timedOut`, labelled with the real timer, `Trip.waited`), whatever was said in between. 😭 is only for a fetch that really failed. A lost ACK gets neither: the next data says the same thing.

To check visuals, run `npm run dev`, then `node scripts/screenshot.mjs` (desktop) or `node scripts/screenshot.mjs http://localhost:5173/ screenshots/phone 390 844`. Screenshots go to `screenshots/` (git-ignored).

## Key concepts

- **Packet vs. PDU snapshot.** A `PacketInfo` is a logical packet (`pk12`, label "SYN"). It keeps its id across hops. A `PduSnapshot` (`pdu40`) is the exact bytes at one moment (e.g. the frame on one link). Every `encapsulate`/`decapsulate`/`tx`/`forward`/`nat:translate` event points at a snapshot. Retransmissions are new packets with `retransmitOf`.
- **Layer numbers** in the sim are TCP/IP 5-layer (1 physical … 5 application).
- **Stream packets** (`kind: 'stream'`) are application bytes handed to TCP or reassembled from it; they never cross a link.
- **Determinism / faults.** Same scenario + seed + FaultPlan ⇒ identical event log. Random loss is keyed by `hash(seed, link, packet)` so adding a manual fault never changes events before it (tested).

## How to add things

- **A new protocol:** add `src/sim/proto/<p>.ts` with `build`, `parse`, `describe` (absolute offsets, explanations), wire it into `decode.ts`, add the name to `Protocol` and `PROTOCOL_LAYER`, add codec tests with known-good bytes.
- **A new scenario:** add `src/sim/scenarios/<name>.ts` returning a `Scenario` (devices with ifaces/routes/ARP seeds/apps, links with real-ish speeds and delays). Add app behaviour in `stack/apps.ts` if needed and a test in the style of `src/sim/run.test.ts`. In the UI, give new device kinds a position in `timeline.ts#POS` (keep cables axis-aligned), a height in `DEVICE_TOP` and a shape in `NetworkScene#buildDevice`; teach `story.ts#chosen` which packets to follow.

## Real-world facts and simplifications (keep honest)

- example.com resolves to Cloudflare addresses; captured values live in `src/sim/scenarios/exampleComCapture.ts` (re-capture with the script). The HTTP response is the verbatim captured bytes (chunked, 932 bytes as of 2026-10-29).
- Home public IP `203.0.113.7` and ISP backbone `198.51.100.0/24` are RFC 5737 documentation ranges standing in for real ones. MAC addresses are plausible but invented.
- The laptop behaves like Linux: TTL 64, ephemeral ports 32768–60999, SYN options MSS/SACK-permitted/timestamps/NOP/window scale 7, glibc DNS timeout 5 s × 2 attempts. TCP RTO follows RFC 6298 (1 s minimum). After a timeout everything still out goes again as the window allows, and a timestamp echo lets the timer recover once a resend is answered, so a short outage costs about its own length plus a timer. The VPN server is a hop both ways, and the web server advertises its normal MSS, knowing nothing of the tunnel.
- Under random loss the DNS lookup often fails: like glibc, the stub resolver sends the question at most twice, 5 s apart. That is the real behaviour, not a bug.
- HTTPS replays a captured session, so its random values, certificate and keys are the real ones from the capture day; the handshake secrets are taken from the key log rather than re-derived from the ECDHE exchange. Cipher suite TLS_AES_128_GCM_SHA256. The card says "hello" for ClientHello/ServerHello, "certificate", "signature" (CertificateVerify), "done" (Finished), "ticket" (NewSessionTicket), "bye" (close_notify).
- The VPN is real WireGuard transport messages (ChaCha20-Poly1305, padded to 16 bytes), but the tunnel is already up: the Noise handshake is not shown and the session keys come from the seeded Rng. MSS is 1380 in a tunnel, as for WireGuard's usual MTU of 1420. Sim tests open the sealed bytes from the ISP line with the session key.
- The phone's Wi-Fi is an open network: real home Wi-Fi encrypts frame bodies (WPA2/WPA3 adds a CCMP header and an 8-byte MIC). No QoS field and no link-layer ACK frames are shown. A real home router bridges its Wi-Fi and Ethernet ports into one network with one address; the sim models that bridge as two interfaces sharing 192.168.1.1 plus a host route to the phone. The phone sends the same captured request bytes as the laptop.
- Simplifications to state in the UI: the real internet path has ~10 routers, we show one ISP router; the resolver answers from cache unless `cold` is on; the LAN is wired Ethernet (Wi-Fi uses 802.11 framing); no IPv6, no TLS in this scenario; ACKs are sent immediately (Linux "quickack" at connection start), not delayed.
- The cold resolver's three upstream servers are the real ones a walk reached on the capture day (`dnsTraceCapture.ts`: a.root-servers.net, then the TLD server and the site's name server its referrals named first with glue), with their real referral and answer bytes and measured round-trip times; the resolver picks the next server from the glue in the bytes, as the capture did. A real resolver talks to many more servers over time, uses QNAME minimisation, EDNS (bigger replies, DNSSEC) and TCP when a reply is truncated; the three hops are the classic textbook walk. The root's `.com` referral is truncated (TC=1, 489 bytes: 13 servers' glue does not fit in 512 bytes without EDNS); the resolver uses what fit, where a real one would ask again over TCP. Replies with a CNAME (info.cern.ch) are followed, but the resolver's own answer to the laptop carries only the addresses. The resolver sends its questions from one port and its service address 1.1.1.1; real resolvers randomise the port per question. When the walk's answer puts another of the site's addresses first (httpbin.org, a cloud load balancer), the web server has that address in a cold run.
- The Wi-Fi link is modelled full duplex with an Ethernet-style preamble; real 802.11 is half duplex with CSMA/CA, and every data frame is answered by a link-layer ACK frame.
- No RACK/TLP: a loss at the tail of a flight waits for the 1 s RTO, where modern Linux sends a probe after about two round trips.
- The thin pipe (option `thin`) is a 20 Mbit/s line whose ISP-side port buffers 8 frames (`THIN_QUEUE`) and tail-drops the ninth: with Linux's initial window of 10 the tenth packet of the first burst falls off, then the FIN at the tail of the second, and TCP mends both with a fast retransmit and NewReno recovery. 8 is a deliberately small, honest knob: a 25-packet photo never stacks more than 8 frames at the port, so a bigger buffer would never overflow here. Real home routers and DSLAMs often buffer hundreds of frames, which hides the loss and makes the queueing delay grow to hundreds of milliseconds instead (bufferbloat). No AQM (CoDel, PIE), no ECN, no per-flow fairness: plain FIFO tail drop, the one frame being clocked out not counted in the buffer.
- The FIN always travels in its own segment; Linux piggybacks it on the last data segment when it can.
- Hosts and routers drop silently: no RST for a closed port and no ICMP for an unreachable address or an expired TTL.
- The NAT always picks a new outside port, a deliberate, visible knob; Linux MASQUERADE keeps the original port unless it collides, though some consumer NATs change it too.
- A name the resolver does not know gets a real NXDOMAIN answer (rcode 3), and the browser gives up on it like a real one; the stub resolver treats an answer without addresses as a failure. A cold resolver whose upstream server stays quiet asks it once more after 2 s, then answers SERVFAIL (rcode 2).
- DHCP (option `dhcp`) is the real four-message exchange with real bytes: DISCOVER and REQUEST broadcast from 0.0.0.0:68 to 255.255.255.255:67, OFFER and ACK unicast to the client's MAC with the offered address as IP destination (what ISC dhcpd and dnsmasq do when the broadcast flag is clear); the client asks for options 1, 3, 6, 15, 28, 51, 54 like dhcpcd/dhclient and resends after 4, 8, 16 s with no ±1 s jitter. The server has fixed leases by MAC (192.168.1.23 for the laptop, .42 for the phone), lease 1 day; no pool, no DECLINE/ARP probe of the new address, no renewal (T1/T2) or RELEASE is shown. A real client's DNS resolver and default route then come from the lease, as here.
